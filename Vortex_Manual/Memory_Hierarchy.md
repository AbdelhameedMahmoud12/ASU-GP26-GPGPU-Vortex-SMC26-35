# 5. Memory Hierarchy

## 5.1. Hierarchical memory system
<div style="display: flex; align-items: center; justify-content: space-between; gap: 0px;">
<div style="flex: 1; text-align: justify;">

The Vortex GPGPU architecture employs a hierarchical memory system designed to optimize both performance and scalability. This hierarchical organization allows for efficient data access across multiple levels, reducing the latency associated with memory operations while maintaining high throughput.
At the lowest latency level, register files provide storage for frequently accessed variables and temporary data generated by active threads. These registers are directly connected to the processing elements, enabling single-cycle access and minimizing data transfer delays.
</div>

<div align ="justify">

Beyond the register files, each processing core or cluster integrates a Level 1 (L1) cache. The L1 cache serves as a fast, intermediate buffer that temporarily holds recently accessed data and instructions, reducing the dependency on slower memory levels.

Above the L1 caches, the system incorporates a shared Level 2 (L2) cache, which acts as a centralized storage layer accessible by multiple cores. This cache level improves data locality and coherence across the GPU by storing data blocks that are likely to be reused by different threads or warps. The global memory (DRAM) represents the largest but slowest level of hierarchy. It accommodates the bulk of program data and requires optimized access mechanisms such as memory coalescing to achieve acceptable performance levels. Overall, the hierarchical memory organization in Vortex GPGPU provides a balanced trade-off between speed, capacity, and power efficiency, ensuring that frequently used data is kept close to the compute units while less critical data resides in larger, slower memory regions.

</div>

## 5.2. Register File
<div align = "justify">
The register file in Vortex serves as a high-speed storage structure that holds the working data for each warp and thread. Conceptually, it acts as the closest memory unit to the execution pipelines, enabling fast read/write operations during instruction execution.

In Vortex architecture, each core maintains its own register file, partitioned per warp to support SIMT (Single Instruction, Multiple Threads) execution. This design ensures that every thread within a warp accesses its dedicated logical registers without conflicts, while still benefiting from shared physical organization.
</div>

### 5.2.1. High-Level Overview
<div style="display: flex; align-items: center; justify-content: space-between; gap: 0px;">
<div style="flex: 1; text-align: justify;">
At a conceptual level, the register file interacts closely with three main components:

- The Warp Scheduler, which issues ready instructions for execution.
- The Scoreboard, which tracks register dependencies and availability.
- The Operand Manager (`VX_operands.sv`), which orchestrates operand fetching and result writeback.

### 5.2.2. Operand Management
<div align ="justify">

The register file operations are managed by the `VX_operands.sv` module.
This unit instantiates multiple Operand Collector (OPC) units, the number of which is determined by the configuration parameter `NUM_OPCS`.
Each OPC handles operand requests for a subset of warps and ensures that data is fetched and delivered to the execution pipelines efficiently.
The outputs of all OPCs are merged by an output arbiter that uses a sticky priority policy, ensuring that multi-cycle operand packets are transmitted without interleaving, preserving data integrity during pipeline operation.
</div>

### 5.2.3. Physical Organization
<div align ="justify">

Within each `VX_opc_unit`, the physical register storage is divided into multiple dual-port RAM banks (`VX_dp_ram`) instances.
This multi-banked design allows concurrent read and write operations across different banks, thereby increasing bandwidth and supporting parallel warp execution.
- **Read Access:** Register addresses are passed through a small crossbar (`req_xbar`) to connect each operand source to the correct bank.
- **Write Access:** The destination register’s bank is selected using a computed index (`gpr_wr_bank_idx`).
- **Concurrency:** Dual-port RAMs provide one read and one write port per bank, enabling simultaneous operand fetch and result writeback in the same clock cycle.
</div>

### 5.2.4. Scoreboarding Mechanism
A scoreboard mechanism coordinates register readiness and dependency tracking across the pipeline.
Implemented within `VX_scoreboard.sv`, the scoreboard monitors the status of each register — whether it is ready for use or awaiting an update.
Before issuing an instruction, the scheduler queries the scoreboard to ensure all source operands are ready, preventing read-after-write (RAW) hazards.
This integration between the scoreboard, operand collectors, and writeback paths allows multiple warps to progress concurrently with minimal stalls, improving overall instruction-level parallelism and throughput.

**Key Takeaways**
- **Organization per Warp:** Logical registers are assigned per warp, mapped dynamically into physical banks for efficient SIMT execution.
- **Distributed across Multiple Banks:** Multiple dual-port RAM banks enable concurrent reads/writes, increasing operand bandwidth.
- **Scoreboarding Mechanism:** Tracks operand readiness and coordinates with the scheduler to prevent hazards and sustain parallel execution.

## 5.3. Memory Banking

### 5.3.1. Definition
<div align="justify">

Memory banking is an architectural technique used to **divide a large memory block into multiple smaller, independently accessible units** known as **banks**. Each bank can process a memory request (read or write) independently within the same clock cycle. This organization enables **parallel memory accesses**, significantly improving the overall **memory bandwidth** and **throughput**, especially in systems that execute many threads simultaneously, such as GPUs.
<div style="flex: 0 0 350px; text-align: center;">
  <img src="https://i.postimg.cc/FzxKXkcY/1.png" alt="Warp Masking Illustration" width="900"/>
  <p style="text-align:center; font-style:italic; color:gray;"></p>
</div>

In a banked memory system, the memory address is mapped to a specific bank based on the lower bits of the address. This mapping ensures that consecutive memory locations are distributed across different  banks rather than being stored sequentially in a single one. As a result, multiple processing elements can access different banks concurrently without interference. 

However, when two or more threads attempt to access the same bank in the same cycle, a bank conflict occurs. In that case, the accesses are serialized, leading to performance degradation.

Memory banking is commonly applied in shared or local memory within GPUs and in DRAM subsystems to exploit data-level parallelism. In architectures such as the Vortex RISC-V GPU, memory banking allows multiple threads (within a warp or workgroup) to access different data elements simultaneously, ensuring high utilization of the on-chip memory bandwidth. Proper data alignment and access pattern optimization are essential to minimize bank conflicts and achieve maximum parallel efficiency. 
</div>

### 5.3.2. Usages Of Memory Banking
<div align ="justify">

The **Vortex RISC-V GPU** employs **memory banking** to efficiently support the high level of **parallelism** inherent in GPU architectures.
Since each core in the Vortex GPU executes a large number of **threads simultaneously**, multiple threads often need to access **shared memory** or **local data** at the same time. If the memory were organized as a single block, these simultaneous accesses would create **contention**, forcing the threads to wait and significantly reducing performance.

To overcome this limitation, the shared memory in Vortex is divided into several **independent memory banks**. Each bank can handle **one access per clock cycle**, allowing multiple threads to read or write data **in parallel**, as long as they access different banks. This structure greatly **increases memory bandwidth** and **reduces access latency**, ensuring that the GPU’s many processing elements remain active rather than idle.

In addition, memory banking helps the **memory controller** distribute requests more evenly across the system, improving the overall efficiency of data movement between **on-chip shared memory**, **L1/L2 caches**, and **off-chip DRAM**.

By supporting parallel memory access and minimizing conflicts, memory banking allows the Vortex RISC-V GPU to achieve **high throughput** and fully utilize its parallel computing capabilities.
</div>

## 5.4. DRAM Memory

### 5.4.1. Definition
<div align ="justify">

**DRAM (Dynamic Random Access Memory)** is a type of **volatile main memory** used in computer and GPU systems to store data and program instructions while the system is running. It is called **dynamic** because each memory cell stores data as an **electric charge in a capacitor**, which gradually leaks over time and must be **refreshed periodically** to retain the stored information.

DRAM is widely used because it offers a **large storage capacity** at a relatively **low cost per bit**, making it ideal for serving as the **global memory** in GPUs like the **Vortex RISC-V GPU**. However, it has **higher latency** and **lower speed** compared to on-chip memories such as caches and registers.

In the Vortex GPU architecture, DRAM acts as the **off-chip global memory**, storing large data sets, program code, and variables required by all processing cores. The GPU accesses DRAM through the **memory controller**, which manages data transfers between DRAM, caches, and shared memory. This hierarchical organization ensures efficient use of bandwidth and minimizes delays in data access during parallel execution.

**DRAM Subsystem:**
- Channel
- DIMM
- Rank
- Chip
- Bank
- Row and Column
</div>

### 5.4.2. Channel
<div align ="justify">

A **DRAM channel** is a **dedicated data path** that connects the **memory controller** to one or more **DRAM modules**.
Each channel operates **independently**, meaning it can handle its own set of **read and write operations** simultaneously with other channels.
A typical DRAM channel includes a **data bus**, **address bus**, and **control signals**, which together allow the processor or GPU to communicate efficiently with the DRAM.
In simple terms, a channel acts like a **separate lane on a highway** — adding more lanes (channels) allows more data to flow at the same time, increasing the total memory bandwidth.

DRAM channels play a crucial role in improving the overall performance and efficiency of the Vortex RISC-V GPU. Each channel provides an independent communication path between the memory controller and the DRAM modules, allowing the system to perform multiple memory operations at the same time. This design enables **parallel data access**, meaning the GPU can access different parts of memory simultaneously. When one channel is busy transferring data, another can process a new request, reducing waiting times and ensuring that the flow of data to the processing cores remains continuous.

Another key advantage of multiple DRAM channels is the increase in **total memory bandwidth**. Since each channel operates independently, adding more channels effectively multiplies the available data throughput. For instance, if one channel provides a certain data rate, two channels can almost double that rate, allowing the GPU to deliver data more quickly to its many cores. This improvement is particularly important for parallel architectures like the Vortex GPU, where large numbers of threads need rapid and simultaneous access to memory.
</div>

### 5.4.3. DIMM and Rank
<div align ="justify">

A **DIMM** (Dual Inline Memory Module) is the **physical circuit board** that holds a number of **DRAM chips** and connects them to the computer or GPU through the memory bus. Each DIMM plugs into a memory slot on the motherboard or GPU board, allowing easy installation and expansion of memory capacity.

DIMMs provide both the **electrical interface** and **mechanical structure** needed for DRAM chips to communicate with the **memory controller**. Modern systems often use multiple DIMMs to increase the total amount of installed memory and to improve performance through parallel access to several memory modules.

Within each DIMM, the DRAM chips are organized into one or more **ranks**. A **rank** is a group of DRAM chips that operate together to form a single 64-bit or 128-bit data interface to the memory controller. When a rank is activated, all of its chips respond simultaneously as if they were a single wide memory device.

Multiple ranks within a DIMM—or across multiple DIMMs—allow the memory controller to **interleave** access between ranks. While one rank is being accessed, another rank can be precharged or prepared for the next access, which improves **memory throughput** and **reduces latency** by overlapping operations.

The use of DIMMs and ranks offers several key **benefits**. DIMMs make it possible to **expand memory capacity** easily by adding or replacing modules without changing the system design. Multiple ranks enhance **parallelism** in data transfers, enabling higher **bandwidth utilization** and **better performance** for memory-intensive workloads. In systems like the **Vortex RISC-V GPU**, this organization helps deliver the large memory capacity and high data rate required for efficient parallel processing, ensuring that the GPU cores receive data quickly and continuously during computation.

</div>

### 5.4.4. Chip and Bank
<div align ="justify">

A DRAM chip is the fundamental building block of dynamic memory. Each chip contains a large array of memory cells, where each cell stores a single bit of data using a capacitor and a transistor. These cells are arranged in a grid of rows and columns, which are accessed through wordlines and bitlines. The DRAM chip includes internal control logic, sense amplifiers, and addressing circuits that allow data to be read from or written to cells.

<div style="flex: 0 0 350px; text-align: center;">
  <img src="https://i.postimg.cc/8cGhbWNc/2.jpg" alt="Warp Masking Illustration" width="500"/>
  <p style="text-align:center; font-style:italic; color:gray;"></p>
</div>

Multiple DRAM chips are combined on a memory module (such as a DIMM) to form a wider data interface, enabling the system to transfer data in larger chunks. For example, eight 8-bit chips can work together to form a 64-bit memory bus. The chip design allows high-density storage in a compact form while maintaining fast access speeds and relatively low power consumption.


Inside each DRAM chip, the memory cells are further organized into smaller, independent units called **banks**. A **bank** is essentially a sub-array within the DRAM chip that can operate **semi-independently** from other banks. Each bank has its own **row buffer**, which temporarily holds the contents of an activated row. When data from a specific address is requested, the corresponding row is opened and its contents are placed in the row buffer, allowing rapid access to that row’s data.

Having multiple banks within a chip enables **bank-level parallelism** — meaning several banks can process memory operations concurrently. While one bank is being accessed or refreshed, another bank can prepare or transfer data, improving overall **throughput** and **reducing idle time** in memory operations.

The main **benefits** of this structure are improved **performance**, **efficiency**, and **bandwidth utilization**. Memory controllers can issue commands to different banks in parallel, which helps hide latency and keep data flowing smoothly to processors such as the **Vortex RISC-V GPU**. In GPU architectures, where thousands of threads require simultaneous access to data, this banking structure ensures **high concurrency** and **low contention**, significantly boosting computational performance.
</div>

### 5.4.5. Row and Column
<div align="justify">
In **DRAM architecture**, memory cells are organized in a two-dimensional structure of **rows** and **columns** within each **bank**. Every memory cell, which stores one bit of data, is located at the intersection of a specific row and column. This organization allows the DRAM controller to access data efficiently by addressing a particular row and column within a chosen bank.
<div style="flex: 0 0 350px; text-align: center;">
  <img src="https://i.postimg.cc/T3SG5JJP/3.jpg" alt="Warp Masking Illustration" width="500"/>
  <p style="text-align:center; font-style:italic; color:gray;"></p>
</div>

Each **row** represents a group of memory cells that can be activated together. When the memory controller wants to access data, it first sends an **Activate** command to open the required row. The contents of that row are then transferred to a small temporary storage area called the **row buffer**. From this row buffer, individual **columns** — which represent smaller segments within the row — can be read or written quickly.In other words, the **row** acts like a “page” of data, while the **column** specifies the exact location within that page.

This row-and-column structure provides several **benefits**. It allows DRAM to store a very large amount of data in a compact and organized form while still offering fast access to specific locations. The use of the row buffer enables rapid **sequential accesses** to data in the same row without the need to repeatedly activate and precharge the memory array.

However, DRAM performance depends heavily on how data is accessed — leading to two important states: **row hit** and **row conflict**.
- A **row hit** occurs when the requested data is located in the **same row** that is already open in the row buffer. In this case, the data can be accessed immediately, resulting in **low latency** and **high performance**.
- A **row conflict** happens when the requested data belongs to a **different row** than the one currently open. The controller must first **precharge** (close) the active row and then **activate** the new row, causing **additional delay** and reducing memory efficiency.
By optimizing memory access patterns to increase row hits and reduce row conflicts, systems can achieve significantly higher throughput. In architectures such as the **Vortex RISC-V GPU**, where many threads access memory simultaneously, efficient row and column management helps minimize latency and maintain consistent data flow between the GPU cores and the DRAM subsystem.
</div>

## 5.5. Cache Architecture
<div align="justify">

The efficiency of modern GPU architecture depends heavily on the design of their on-chip memory hierarchy. To sustain massive thread-level parallelism, data must be supplied to execution units at high bandwidth and minimal latency. This is achieved through a multi-tier memory system that integrates programmable and hardware-managed components within the GPU core complex.

In the Vortex GPGPU, the on-chip memory hierarchy is organized into three principal levels.
- At the core level, Local (Shared) Memory provides fast, software-managed storage that enables inter-thread communication and data reuse.
- At the cluster level, the L1 Cache Memory serves as a hardware-controlled buffer for both data and instructions, accelerating frequent memory access.
- Finally, a unified L2 Cache Memory spans all clusters, maintaining coherence and reducing external DRAM bandwidth demand.

### 5.5.1. Local Shared Memory
Local Memory (also known as Shared Memory) is a high-speed, on-chip memory space shared by threads within a single core. It is a key component of the memory hierarchy, positioned between the private register file of individual threads and the higher-level caches (L1/L2) and global memory.

As a software-managed memory, it provides programmers with explicit control over data placement and access, making it a powerful tool for performance optimization. Access to this memory is handled by the Load/Store Unit (LSU) within the core, and memory requests are routed to it by the `VX_lmem_switch` module based on the address space.

The primary purpose of Local Memory is to facilitate efficient data sharing and reuse among threads in a cooperative group. Its main roles include:
- **Data Reuse:** It serves as a user-managed cache to store frequently accessed data from global memory. By loading data into Local Memory once, multiple threads can access it repeatedly with much lower latency, significantly reducing traffic to the global memory.
- **Inter-Thread Communication:** Threads within the same core can use Local Memory to exchange data, enabling them to collaborate on solving a larger problem. This is essential for a wide range of parallel algorithms, such as reductions, convolutions, and matrix transpositions.
- **Latency Reduction:** By providing a fast, on-chip data path, Local Memory helps to hide the high latency associated with global memory accesses. This is a critical aspect of achieving high performance in memory-bound applications.
Local Memory in Vortex is implemented in the `VX_local_mem.sv` module. It is designed as a high-speed, on-chip Static RAM (SRAM), which offers much lower latency and higher bandwidth compared to the off-chip DRAM used for global memory.

**Scope of Access:** The memory is accessible only by threads within the same core. It is not visible to threads in other cores, nor can it be accessed by the host CPU.

### 5.5.2. L1 Cache Memory
The L1 cache is the first level of hardware-managed cache in the Vortex GPGPU memory hierarchy. It is positioned between the processing cores and the L2 cache, serving as a high-speed buffer for frequently accessed instructions and data. Its primary purpose is to reduce memory access latency and to lower the bandwidth demands on the higher levels of the memory system (L2 cache and global memory).

In the Vortex architecture, the L1 caches are instantiated within the `VX_socket.sv` module, meaning they are shared by the group of cores within that socket.

Vortex implements a split L1 cache architecture, which is a common design in high-performance processors. This means there are two separate L1 caches:
- **L1 Instruction Cache (I-Cache):** This cache is dedicated to storing recently fetched instructions. By having a separate cache for instructions, the fetch stage of the pipeline can retrieve instructions without competing for resources with data memory accesses from the execution units.
- **L1 Data Cache (D-Cache):** This cache is used for load and store operations. It stores data that is read from or written to memory by the Load/Store Unit (LSU).
This separation prevents structural hazards between instruction fetches and data accesses, improving overall pipeline efficiency.

Each core in a cluster issues memory requests through its Load/Store Unit (LSU). These requests are forwarded to the cluster’s L1 cache subsystem, implemented in the module `VX_socket.sv`. The L1 cache responds to three primary types of traffic:
- Data Load/Store requests from LSUs.
- Instruction Fetches from each core’s fetch pipeline.
- Coherence and refill transactions to and from the L2 cache.
By filtering and serving most accesses locally, the L1 cache substantially reduces the frequency of off-chip transactions.

| Component | Function |
| --- | --- |
| Tag Store | Holds the metadata (tags, valid bits, dirty bits) to determine cache hits or misses. |
| Data Store | Stores the actual cached data (cache lines). |
| MSHR (Miss Status Holding Register) | Tracks outstanding miss and merges duplicate requests. |
| Replacement Unit | Select which cache line to evict on a miss when the cache is full. |

These components interact tightly within the `VX_cache_core.sv` logic, which handles arbitration, request pipelining, and communication with the L2 cache.
When a memory request arrives from a core:
1. The Tag Store is accessed to check whether the requested address exists in the cache (tag comparison).
2. If a hit occurs, the Data Store provides the data directly to the LSU or fetch unit.
3. If a miss occurs, the MSHR allocates a new entry, forwards the request to the L2 cache, and temporarily tracks it.

**Summary:**
The L1 Cache Memory in Vortex GPGPU provides fast, hardware-managed storage shared among cores in the same cluster. Its architecture — comprising Tag Store, Data Store, MSHR, and Replacement Unit — delivers low-latency access and efficient miss handling. Positioned between the Local Memory and the unified L2 Cache, it plays a central role in sustaining high memory throughput and reducing access latency across the GPU pipeline.

### 5.5.3. L2 Cache Memory
The L2 cache is the second level of hardware-managed cache in the Vortex GPGPU. It serves as a large, unified cache shared by all the processing cores within a single cluster. Positioned between the L1 caches and the optional L3 cache or main memory, its primary role is to reduce memory access latency, absorb traffic from the L1 caches, and minimize costly accesses to the slower, off-chip global memory (DRAM).

By acting as a large, shared buffer, the L2 cache is critical for application performance, especially for workloads with large data sets or irregular memory access patterns that would otherwise cause frequent misses in the smaller L1 caches.

The L2 cache is a vital mid-level component in the Vortex memory hierarchy:
- **Shared Resource:** Unlike the L1 caches, which are typically scoped to a smaller group of cores (a "socket"), the L2 cache is shared by all cores within a larger "cluster." This allows for efficient data sharing between cores in the same cluster without needing to go to main memory.
- **Victim Cache:** It primarily acts as a victim cache for the L1 caches. When a cache line is evicted from an L1 cache, it is placed in the L2 cache. This ensures that recently used data, even if evicted from L1, remains available in a fast, on-chip location.
- **Traffic Aggregator:** It aggregates memory requests from all the L1 caches in the cluster, helping to reduce the number of individual requests sent to the main memory controller and improving overall memory bandwidth utilization.
The L2 cache is a highly configurable and robust component built from several key modules.
- **Instantiation:** The L2 cache is instantiated within the `VX_cluster.sv` module. It is implemented using the generic `VX_cache_wrap.sv` module, which is configured with the L2-specific parameters.
- **Unified Cache:** It is a unified cache, meaning it stores both instructions and data. This contrasts with the split L1 I-Cache and D-Cache design and allows the L2 to dynamically allocate its space based on the application's needs.
- **Banked Design:** To handle numerous simultaneous requests from the L1 caches, the L2 cache is designed with multiple independent banks (configurable via `L2_NUM_BANKS`). This banked architecture allows for parallel memory accesses, significantly increasing throughput, as long as the requests target different banks.
The operation of the L2 cache is managed entirely by hardware and is transparent to the software.
- **Request from L1:** An L1 cache (either I-Cache or D-Cache) experiences a miss and sends a memory request to the L2 cache.
- **L2 Cache Lookup:** The L2 cache checks its tags to see if it contains the requested data.
- **L2 Cache Hit:** If the data is found:
    - The data is retrieved from the appropriate L2 cache bank.
    - It is sent back to the requesting L1 cache.
    - The L1 cache stores the data and forwards it to the core.
- **L2 Cache Miss:** If the data is not in the L2 cache:
    - An MSHR entry is allocated to track the miss.
    - A memory request is generated and sent to the next level in the hierarchy (the L3 cache, if enabled, or the main memory controller).
    - When the data returns from memory, it is stored in the L2 cache (and potentially an L1 cache simultaneously, depending on the fill policy).
    - The data is then forwarded to the requesting L1 cache and core.

## 5.6. Memory Optimization & Scheduling
High-performance computing in a GPGPU is fundamentally limited by memory bandwidth and latency. The Vortex architecture addresses this bottleneck with a dedicated and highly structured memory front-end that aggressively optimizes and schedules requests before they are issued to the cache hierarchy and main memory. This system is designed to achieve two primary goals: maximize the effective bandwidth of the memory system by reducing redundant traffic, and hide the inherent latency of DRAM by decoupling the core pipeline from memory stalls.

The strategy is a two-stage process: first, optimization via memory coalescing, and second, scheduling via queuing and channel-aware batching.

Two modules form the foundation of this system:
- `VX_mem_coalescer.sv`: A specialized hardware unit responsible for the critical optimization of merging multiple, fine-grained memory requests into a single, coarse-grained memory transaction.
- `VX_mem_scheduler.sv`: A comprehensive management module that serves as the primary interface between the core's Load/Store Unit (LSU) and the memory subsystem. It orchestrates the entire flow, integrating the coalescer and managing request/response traffic.
Memory coalescing is the single most important optimization for bandwidth-bound GPU workloads.

**Concept:**
A GPU warp consists of multiple threads executing in lockstep. When these threads access memory, they often access locations that are adjacent to one another. Instead of issuing N separate memory requests (where N is the number of threads), the coalescing hardware detects this access pattern and merges, or *coalesces*, them into a single, wide memory transaction that covers the entire address range.

**Implementation in `VX_mem_coalescer.sv`:**
The Vortex coalescer is a parameterized module that operates as follows:
1. **Intake:** It accepts a block of `NUM_REQS` parallel requests, each with its own address, data, and byte-enable mask.
2. **Seed Selection:** It selects a "seed" request from the incoming block.
3. **Address Matching:** It compares the block-aligned address of the seed request against all other requests in the block. All requests that fall within the same physical memory line (e.g., a 64-byte aligned block) are identified as a coalescing group.
4. **Transaction Merging:** It generates a new, single memory request. The address of this request is the base address of the memory line. The byte-enables and write-data (for stores) are meticulously merged from all constituent requests into the single wide transaction.
5. **Dispatch:** This newly formed, wide request is what gets issued to the next level of the memory hierarchy.
6. **Response De-Muxing:** Upon receiving a response for the wide transaction, the coalescer uses stored offset information for each original request to extract and route the correct data word back to each individual requester.
**Architectural Benefit:** This mechanism converts multiple, potentially inefficient, narrow memory accesses into a single, highly efficient, wide access that perfectly matches the burst nature of modern DRAM and the line size of the cache hierarchy. This drastically reduces transaction overhead and maximizes data throughput per cycle.

## 5.7. Memory Access Flow
The memory access flow describe how are the memory requests handled starting from the LSU (Load - Store Unit) through the whole memory hierarchy according to hits and misses throughout the different levels of cache until the stored data is returned.

### 5.7.1. Memory Access Initiation
The memory component in this part is the Load-Store Unit (LSU). The memory access process begins with a load or store instruction from the execution process of an active thread. The LSU calculates the effective memory address by adding the base register value with any offset value specified in the instruction. Then it packs this information to a memory request which includes the operation type, address, size, and the thread ID. Then this memory request is sent to the Memory Unit which decides how will the request be processed in the memory hierarchy.

### 5.7.2. Memory Unit Processing
The memory component in this part is the Memory Unit. The Memory Unit acts as an interface between the LSU and the memory hierarchy. It determines whether the memory request will access shared memory, local memory, or a global memory based on the packed information in the request then it routes the request to the correct destination typically starting with the L1 cache for the local data. The memory Unit also coordinates the memory response tracking ensuring that the returned data from memory is delivered to the correct thread group as said an interface between the LSU and memory hierarchy.

### 5.7.3. Cache Access
The memory component in this part is the L1 cache. The L1 cache is the first level in memory hierarchy for data lookup. When the Memory Unit sends the memory request to the L1 cache it checks the tags to determine whether its present (cache hit) or its missing (cache miss). For a cache hit the request is immediately sent back to the Memory Unit to deliver it back to the LSU. As for a cache miss the request is passed to the Miss Status Handling Register (MSHR) for further processing. This stage is very important as most frequent used data is served directly from the L1 cache which reduces latency, minimize global memory traffic, and improve the throughput across threads.

### 5.7.4. Miss Handling
The memory component in this part is the Miss Status Handling Register (MSHR). When a cache miss occurs the MSHR allocates an entry to track pending memory request. Each entry records the memory address, requesting warp ID and data size. This allows multiple concurrent misses to be managed efficiently. If another miss happens for same address while the miss request is pending the MSHR coalescer (groups) these requests merging them to avoid redundant accesses to lower memory levels. Once everything is organized the MSHR forwards the request to the Memory Coalescer.

### 5.7.5. Memory Request
The memory component in this part is the Memory coalescer. The memory Coalescer groups and optimizes memory requests from multiple threads or warps. In GPGPUs threads often access consecutive memory addresses which allows the coalescer to combine the requests into a single wide memory transaction. What this does is it reduces memory bandwidth pressure and improves efficiency. Once these requests are grouped the Memory Coalescer forwards them to L2 cache for further lookup.

### 5.7.6. Memory Response
The memory component in this part is the L2 cash and the Main Memory. The L2 cache serves as a shared memory between cores it checks whether the requested data exists within its storage if its present then a hit occurs and the data is sent back immediately to the MSHR if there is a miss then the request continues to the Main Memory (DRAM) once the data is retrieved from the Main memory is climbs up the hierarchy back to the LSU. Along the way caches could update with this fetched data so for future accesses it will be faster.

### 5.7.7. Result Writeback
The memory components in this part is the Memory Unit and LSU. After the data is fetched the Memory Unit forwards is to the LSU for the write back phase. For load instruction the loaded value is written into the destination register file of the requesting thread. As for the store instruction the LSU confirms that the data has been successfully stored in memory.

### 5.7.8. Summary
The memory access flow in the Vortex GPGPU represents the complete process of how memory operations are initiated, processed, and completed. It begins with the Load-Store Unit (LSU) generating a memory request and continues through multiple stages of the memory hierarchy, including the Memory Unit, L1 Cache, MSHR, Memory Coalescer, L2 Cache, and Main Memory. Each component plays a specific role from calculating addresses and routing requests to handling cache hits and misses, merging similar requests, and retrieving data from memory. The process ends with the Result Writeback stage, where the fetched data is written back to the register file or confirmed as stored in memory. This structured flow allows the GPGPU to handle thousands of parallel memory requests efficiently, reduce latency through caching and coalescing, and maintain high throughput across all active threads.

## 5.8. Memory Performance
The vortex architecture integrates several mechanisms to enhance memory performance and improve data throughput across GPU pipeline. These mechanisms aim to minimize conflicts, reduce latency, and maintain efficiency in multi-threaded execution environments.

### 5.8.1. Bank Conflicts
Bank conflicts occur when multiple memory requests target the same memory bank at the same time. These conflicts cause serialization of accesses to the memory which cause a performance degradation. To minimize this issue Vortex employs a multi banked memory structure that allow concurrent accesses to different banks. Crossbar interconnects route the requests among the banks while the intelligent request scheduling helps to distribute memory accesses evenly across banks.

### 5.8.2. Memory latency Hiding
Memory latency can affect performance significantly when waiting for data to return from memory Vortex reduces this issue using multiple strategies. Thread-level parallesim allows Vortex to change warps during execution so that while one warp is waiting for memory other warps continue executing. MSHR track the pending request its address and requested thread allowing other executions to continue. Also, non-blocking caches allows the instruction execution to continue even when a miss occur. Additionally, memory coalescing minimizes the total number of transactions.

### 5.8.3. Cache Coherence
The Vortex architecture uses a simplified cache coherence model to maintain consistency across the memory system. For the L1 cache there is no direct coherence between them as they are private. Instead coherence is maintained at the shared cache levels where all threads can synchronize their memory view.

### 5.8.4. Summary
Vortex employs several mechanisms to enhance memory performance. **Bank conflicts** are reduced through multi-banked memory structures, crossbar interconnects, and smart scheduling. **Memory latency** is hidden using techniques like thread-level parallelism, Miss Status Handling Registers (MSHRs), non-blocking caches, and memory access coalescing to keep execution running smoothly during misses. Finally, **cache coherence** is maintained through a simplified model — private L1 caches are not coherent, while coherence is enforced only at shared cache levels (L2/L3) or managed by software when required.

## 5.9. Memory Configuration
The entire memory hierarchy of the Vortex GPU can be fine-tuned using pre-processor macros in the `VX_config.vh` file. These parameters control the presence, size, associativity, and behavior of each level of the memory system.

**Top-Level Memory Configuration**
- `MEM_ADDR_WIDTH`: Sets the global addressable memory space (Default: 32 or 48 bits).
- `MEM_BLOCK_SIZE`: The fundamental block size for memory transactions, used as the default cache line size (Default: 64 bytes).

**GPR Configuration**
- `NUM_WARPS`: Sets the number of resident warps per core (Default: `4`).
- `NUM_THREADS`: Sets the number of threads per warp (Default: `4`).
- `NUM_GPR_BANKS`: The number of parallel banks in the register file (Default: `4`).
- `XLEN`: The bit-width of each register (Default: `32`).

**LSU Configuration**
- `LSUQ_IN_SIZE` & `LSUQ_OUT_SIZE`: Depth of the LSU's input and output queues.
- `LSU_LINE_SIZE`: The width of a memory access performed by the LSU in bytes.

**Local Memory (LMEM) / Shared Memory Configuration**
- `LMEM_ENABLE`: Enables or disables the LMEM block.
- `LMEM_LOG_SIZE`: Log-base-2 of the LMEM size in bytes (Default: `14` for 16 KB).
- `LMEM_NUM_BANKS`: Number of parallel banks in the LMEM.

**L1 Cache Configuration**
- `L1_DISABLE`: Disables both I-Cache and D-Cache.
- `ICACHE_ENABLE` & `DCACHE_ENABLE`: Toggles for the I-Cache and D-Cache.
- `ICACHE_SIZE` & `DCACHE_SIZE`: Total size of each cache in bytes (Default: 16 KB).
- `ICACHE_NUM_WAYS` & `DCACHE_NUM_WAYS`: Set-associativity of each cache (Default: 4-way).
- `DCACHE_NUM_BANKS`: Number of parallel banks in the D-Cache.
- `DCACHE_WRITEBACK`: Write policy (`0` for write-through, `1` for write-back).
- `ICACHE_REPL_POLICY` & `DCACHE_REPL_POLICY`: Replacement policy (e.g., PLRU).
- `ICACHE_MSHR_SIZE` & `DCACHE_MSHR_SIZE`: Number of Miss Handling Register entries.

**L2 Cache Configuration**
- `L2_ENABLED`: Enables or disables the L2 cache.
- `L2_CACHE_SIZE`: Total size in bytes (Default: 1 MB).
- `L2_NUM_BANKS`: Number of parallel banks.
- `L2_NUM_WAYS`: Set-associativity (Default: 8-way).
- `L2_WRITEBACK`: Write policy (Default: write-through).
- `L2_REPL_POLICY`: Replacement policy.
- `L2_MSHR_SIZE`: Number of MSHR entries.
